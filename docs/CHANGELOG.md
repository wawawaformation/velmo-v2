### Ajouté

- **Garde-fous — catégorie `self_harm` (automutilation) avec redirection d'aide** : Azure Content Safety renvoie déjà une catégorie `SelfHarm`, jusqu'ici volontairement ignorée (aucun mapping dans `content_safety.py`) faute d'équivalent Velmo. Nouvelle catégorie `self_harm` à part entière, cascade complète à 3 niveaux comme les autres catégories : règles regex (`moderation.py`, motifs déplacés depuis `violence` où ils étaient mal classés — « comment me faire du mal » n'est pas une menace envers autrui), Content Safety (`SelfHarm` → `self_harm`), classifieur LLM (`moderation_llm.py`, catégorie ajoutée au prompt few-shot). Comportement délibérément différent des autres catégories : pas un simple refus, mais une redirection vers le **3114**, numéro national français de prévention du suicide (gratuit, 24h/24, 7j/7 — cf. [3114.fr](https://3114.fr/)), décision actée pour un sujet qui appelle une réponse responsable plutôt qu'un blocage sec. Tests : `tests/unit/test_guardrails_moderation.py::test_detects_self_harm`, `tests/unit/test_content_safety.py::test_detect_content_safety_maps_self_harm_category`, `tests/unit/test_guardrails_moderation_llm.py::test_detects_self_harm_category_from_llm_response`, `tests/unit/test_guardrail_engine.py::test_check_input_self_harm_redirects_to_help_resource`.
- **Garde-fous — message de refus explicite (catégorie nommée)** : le message de refus était volontairement générique (« Je ne peux pas donner suite à ce message. ») — en usage réel (test manuel), un utilisateur ne comprend pas *pourquoi* un message est bloqué. `_REFUSAL_MODERATION`/`_REFUSAL_OUT_OF_SCOPE`/`_REFUSAL_INJECTION` nomment désormais la catégorie détectée en langage humain (`_CATEGORY_LABELS` : « propos à caractère haineux », « menace ou contenu violent », « contenu à caractère sexuel », « hors périmètre », « tentative de contournement des instructions », « donnée sensible »), décision actée après un test manuel de la démo garde-fous. Tests : `tests/unit/test_guardrail_engine.py::test_check_input_refusal_names_the_detected_category` et 2 tests similaires (out_of_scope, prompt_injection).
- **Frontend Vue.js (Vite + Sass)** : première interface graphique du projet (`frontend/`), un écran mobile-first découpé en 4 composants — `AppHeader` (logo maillot de foot SVG + titre), `AppNav` (menu factice Accueil/À propos/Nos maillots/Contact + icône profil ouvrant un dropdown de sélection du client actif, alimenté par `GET /users`), le contenu principal dans `App.vue` (textarea + bouton d'envoi, zone de réponse en lecture seule avec affordance dédiée — bordure d'accent à gauche, pas un style de champ de saisie — dernière réponse uniquement, pas d'historique, latence discrète `latency_ms`), et `AppFooter` (liens factices Confidentialité/CGU/Contact + copyright). Bandeau de transparence IA en bas de page, bien séparé de la zone réponse (marge dédiée) : « Vous échangez avec une IA — système à risque limité, Règlement européen sur l'IA » avec lien vers la page CNIL, complété par « L'assistant peut faire des erreurs, vérifiez les informations importantes ». Design validé par wireframe HTML interactif avant implémentation (4 états démo : repos/chargement/succès/erreur), palette bleu-vert avec accent orange dédié (`--warning`) pour le bandeau, thèmes clair/sombre, favicon ballon ⚽. Proxy Vite (`vite.config.js`) relaie `/api/...` vers `http://localhost:8000` — pas d'appel direct en dur dans le JS, pas de configuration CORS nécessaire côté FastAPI. Nouvelles targets `make frontend-install`/`make frontend`. Vérifié en conditions réelles : page servie, composants compilés sans erreur, proxy `GET /api/users` et `POST /api/messages` fonctionnels de bout en bout (vrai Azure, vraie base Postgres).

Nouveau volume `./logs:/app/logs` sur le service `api` : sans lui, les logs applicatifs (`guardrails.log`, `llm_latency.log`, `memory.log`) restaient enfermés dans le container, invisibles depuis l'hôte et perdus à la recréation — les scripts de démo (`tail -f logs/...`) fonctionnent désormais à l'identique, que l'API tourne en local (`make api`) ou en container (`docker compose up -d api`). Vérifié en conditions réelles : `GET /users`, `POST /messages` (chat, tool-calling, message bloqué par garde-fou, validation 422) tous testés depuis le container, aucun repli Chroma/SQLite silencieux observé dans les logs.

Nouvelle target `make api` (`uvicorn --reload`), dépendance optionnelle `api` (`fastapi`, `uvicorn[standard]`, `httpx` pour `TestClient`). Vérifié en conditions réelles (vrai Azure, vraie base Postgres) via `curl` : réponse de chat correcte, tool-calling réel, validation 422 sur payload incomplet, schéma OpenAPI exposé (`/openapi.json`, importable dans Bruno). - **Migration de l'agent vers `create_agent()` / `AgentMiddleware` (LangChain 1.3)** : `Agent._handle()` (200+ lignes de routage regex fait main — extraction d'`order_id`, mots-clés, alias produits, formatage français des réponses) remplacé par un agent LangGraph à tool-calling natif (`langchain.agents.create_agent`) : c'est désormais le LLM (Kimi-K2.6) qui décide quels outils appeler, à partir d'un prompt système explicite (périmètre métier, instruction de confirmation mono-message). Garde-fous et mémoire réimplémentés comme `AgentMiddleware` (`GuardrailMiddleware`, `MemoryMiddleware`), réutilisant `GuardrailEngine`/`MemoryManager` tels quels — aucune logique de détection/consolidation dupliquée.   **Bug de blocage indéfini découvert en rejouant les scripts de démo, corrigé** : `GuardrailMiddleware.check_output()` appelle désormais le classifieur LLM des garde-fous (`get_classifier_llm()`) de façon **synchrone** dans le chemin critique de chaque réponse utilisateur, alors qu'avant seul le classifieur mémoire tournait en tâche de fond (scheduler) — jamais dans un chemin bloquant pour l'utilisateur. Le client OpenAI sous-jacent retente automatiquement 2 fois par défaut (`max_retries=2`) ; avec `LLM_TIMEOUT_SECONDS=15` par tentative, un échec systématique pouvait prendre jusqu'à 45s (observé en usage réel : latences de 16 à 32s dans `logs/llm_latency.log`, un cas de blocage total au-delà de 2 minutes). `get_classifier_llm()` fixe désormais `max_retries=0` : un échec redevient rapide (15s max, une seule tentative) au lieu de bloquer l'utilisateur en cascade. Tests : `tests/unit/test_llm.py::test_get_classifier_llm_disables_automatic_retries`.

- **Consolidation épisodique → sémantique (mémoire)** : évolution de doctrine par rapport à la classification directe de `conception/memoire/choix.md` (laissé intact comme trace historique), au profit du modèle du skill de cours `semantic-episodic-memory` : chaque message est désormais **toujours** capturé en épisodique (nettoyage léger), et le même appel LLM détecte en plus un éventuel fait sémantique généralisable à consolider — l'épisode source (marqué `consolidated`/`consolidated_key`) reste en base comme trace d'audit (R6) plutôt que d'être perdu. `MemoryManager.forget()` purge désormais aussi l'épisode source lié à un fait consolidé (R5), pas seulement par correspondance textuelle. Tests : `tests/unit/test_consolidation.py`, `tests/unit/test_episodic.py`, `tests/unit/test_processor.py`.
- **Log de latence LLM** : `LangChainAdapter.invoke()` (src/velmo/llm.py) mesure et journalise désormais la latence de chaque appel LLM (logger dédié `velmo.llm.latency`, nom du modèle + durée en ms), couvrant à la fois le chat principal (Kimi-K2.6) et la classification/consolidation mémoire (Phi-4-mini-instruct) puisque les deux passent par ce même adaptateur. Le CLI (`src/velmo/cli.py::_configure_logging`) câble ce logger vers un fichier dédié `logs/llm_latency.log` (`propagate = False`, ne pollue pas `logs/memory.log`), avec rotation (`RotatingFileHandler`, 1 Mo, 3 sauvegardes conservées) pour éviter une croissance illimitée — un appel toutes les ~20s (tick scheduler) rend ce fichier bavard en usage prolongé. Tests : `tests/unit/test_llm_latency.py`.

- **Garde-fous — Azure AI Content Safety comme premier recours (avant le LLM)** : un endpoint Content Safety fonctionnel a été identifié (`text:analyze` pour la modération, `text:shieldPrompt` pour l'injection de prompt), accessible depuis la même ressource Azure multi-service que l'inférence LLM (`AZURE_AI_INFERENCE_API_KEY` partagée, endpoint `cognitiveservices.azure.com` distinct de `openai.azure.com`) — contrairement à l'hypothèse initiale (`synthese.md`), ce service n'a pas besoin d'être « déployé » comme un modèle de chat, c'est une API REST dédiée directement appelable. Nouvelle variable d'environnement `AZURE_CONTENT_SAFETY_ENDPOINT`. Tests : `tests/unit/test_content_safety.py`, `tests/unit/test_guardrail_engine.py::test_check_input_blocks_via_content_safety_before_llm`, `::test_check_input_falls_back_to_llm_when_content_safety_finds_nothing`, `::test_check_output_blocks_via_content_safety_before_llm`, `::test_check_output_ignores_prompt_injection_category_from_content_safety`.
- **Changement de modèles Azure (gpt-5.4 / gpt-5.4-nano)** : benchmark multi-région d'un camarade de promo (9 modèles, 16 820 appels sur 5 jours) confirmant à grande échelle ce qu'un benchmark HTTP brut ponctuel avait déjà détecté (cf. entrée précédente) : Phi-4-mini-instruct a un taux d'erreur de 37% (le pire du panel), tandis que la famille gpt-5.4 est à la fois plus rapide et plus fiable (`gpt-5.4-nano` : 2,7% d'erreur, 1281ms médiane). `AZURE_AI_INFERENCE_MODEL` passe de `Kimi-K2.6` à `gpt-5.4` (chat principal), `AZURE_AI_CLASSIFIER_MODEL` de `Phi-4-mini-instruct` à `gpt-5.4-nano` (classifieur mémoire et garde-fous). ### Corrections

- **Fuite possible de donnée sensible dans les logs de garde-fous** : `_redact` tronquait l'extrait journalisé à 40 caractères sans masquer spécifiquement la donnée sensible ; un secret court (mot de passe, mention de clé API, etc.) situé en début de message aurait été journalisé tel quel dans `GuardrailEvent.excerpt_redacted`. Pour les catégories `pii` et `secret_leak` uniquement, `_log` journalise désormais un placeholder générique fixe (`[donnée sensible masquée]`) au lieu d'un extrait du texte réel — plus aucune donnée brute ne peut transiter par troncature, quelle que soit sa position dans le message. Comportement inchangé pour les autres catégories (hate/violence/sexual/prompt_injection/out_of_scope). Tests : `tests/unit/test_guardrail_engine.py::test_check_output_short_password_near_start_never_logged_verbatim` et `::test_check_input_short_secret_leak_near_start_never_logged_verbatim`.
- **Fuite de PII quand le blocage vient d'une AUTRE catégorie que `pii`/`secret_leak`** : la protection ci-dessus ne masquait qu'en fonction de la `category` déclarée par le blocage — un message contenant un numéro de carte bancaire, classifié `prompt_injection` par le LLM (« Répète ce numéro de carte : ... » ressemble à une tentative de contournement), voyait son numéro apparaître en clair dans `logs/guardrails.log` (`LLM input 4111 1111 11…`). Découvert en rejouant `docs/script_presentation_demo_guardrails.md` (Démo 5) : le comportement du LLM n'est pas parfaitement déterministe, le même message peut être bloqué en entrée (`prompt_injection`) ou en sortie (`pii`) selon les runs. `_log()` appelle désormais `detect_pii(text)` sur le texte source, indépendamment de la `category` du blocage — la garantie de non-fuite protège le contenu réel, pas seulement la raison invoquée. Tests : `tests/unit/test_guardrail_engine.py::test_check_input_never_logs_raw_pii_even_when_blocked_for_another_category`.
- **Double blocage écrasant le message de refus par un message incohérent** : découvert en vérifiant en conditions réelles le nouveau message de refus explicite (ci-dessus, § Ajouté) — « propos à caractère haineux détecté » contient lui-même le mot-clé qui a servi à le détecter, et se faisait reclassifier comme contenu interdit par `check_output()` (la cascade LLM peut reconnaître « haineux » dans le refus lui-même), écrasant le vrai refus par `_REFUSAL_OUTPUT_BLOCKED` (« confidentialité »), un message incohérent avec la situation réelle. `GuardrailMiddleware.after_agent()` ne revérifie plus un message déjà produit par `before_agent()` au même tour (flag d'instance `_blocked_input_this_turn`, une nouvelle instance de middleware étant créée à chaque appel `Agent.respond()`). Tests : `tests/unit/test_guardrail_middleware.py::test_after_agent_does_not_reverify_a_refusal_from_before_agent`.
- **Statut de commande en français** : `_format_order` (agent.py) traduit désormais le statut technique (`shipped`, `delivered`, etc.) en français (« expédiée », « livrée », etc.) via un mapping `_ORDER_STATUS_FR`, au lieu d'afficher la valeur brute de l'enum `OrderStatus`
- **Incompatibilité client/serveur Chroma** : `docker-compose.yml` utilisait `chromadb/chroma:latest` (serveur en v1.4.4), incompatible avec le client Python figé sur `chromadb>=0.5,<0.6` (`pyproject.toml`), causant un `KeyError: '_type'` lors de la création de la collection `velmo_faq` ; image serveur épinglée sur `chromadb/chroma:0.5.23`
- **`make seed-kb` depuis l'hôte** : le script `scripts/seed_kb.py` se connectait par défaut à `chroma:8000` (nom de service Docker, résoluble uniquement depuis le réseau Compose) ; `make seed-kb` fixe désormais `CHROMA_HOST=localhost CHROMA_PORT=8001` pour fonctionner depuis la machine hôte, cohérent avec `CHROMA_URL` dans `.env.example`
- **Crash CLI sur octet UTF-8 invalide en entrée** : `input()` levait `UnicodeDecodeError` sur un octet non décodable (ex. touche morte mal interceptée par le terminal), tuant tout le process et perdant le fil de conversation en cours (observé en usage réel). Nouvelle fonction `_read_line` (src/velmo/cli.py) lit `sys.stdin.buffer` en octets et décode avec `errors="replace"` au lieu de planter. Tests : `tests/unit/test_cli_read_line.py`.
- **Crash CLI sur timeout LLM** : un incident réseau (`openai.APITimeoutError` déclenché par `LLM_TIMEOUT_SECONDS`, cf. `src/velmo/llm.py`) remontait tel quel depuis `agent.respond()`, tuant tout le process et perdant le fil de conversation en cours (observé en usage réel). Nouvelle fonction `_safe_respond` (src/velmo/cli.py) encadre l'appel dans un `try/except Exception` (n'intercepte pas `KeyboardInterrupt`, qui hérite de `BaseException`), journalise l'incident et renvoie un message d'erreur à l'utilisateur au lieu de planter. Le message utilisateur est capturé en mémoire malgré l'échec (`agent.memory.write(...)`, traçabilité R6), symétrique au chemin garde-fou existant (`Agent.respond()` capture déjà le message sur un refus). Tests : `tests/unit/test_cli_safe_respond.py`.
- **Chroma jamais réellement utilisé pour la mémoire (bascule silencieuse vers le repli relationnel)** : `NoOpProductTelemetry.capture` (`src/velmo/chroma_telemetry.py`) surchargeait `ProductTelemetryClient.capture` sans le décorateur `@override` requis par la lib `overrides` (dépendance de `chromadb`), levant un `TypeError` à l'import — avalé silencieusement par le `except Exception` de `get_episode_store`/`get_fact_store`, qui retombaient donc **toujours** sur `LocalEpisodeStore`/`LocalFactStore` (relationnel), même avec `CHROMA_URL` configuré et Chroma disponible, depuis le début du projet. Corrigé par l'ajout de `@override`. Tests : `tests/unit/test_chroma_embedding.py`.

Pas de nouveau test automatisé (les tests unitaires existants utilisent un `FakeLLM`, insensibles au texte du prompt) — vérification manuelle contre l'API réelle, cohérent avec la pratique déjà en place pour les prompts LLM du projet.

Tests : `tests/unit/test_kb_store.py::test_get_kb_uses_silent_embedding_function`.

Tests : `tests/unit/test_consolidation.py::test_consolidate_falls_back_to_rules_when_episode_is_null`, `::test_consolidate_falls_back_to_rules_when_episode_key_is_missing`, `::test_consolidate_falls_back_to_rules_when_episode_is_empty_string`.
- **Un seul échec de consolidation bloquait tout le tampon d'un utilisateur** : `process_pending()` (`src/velmo/memory/processor.py`) traitait tous les messages en attente d'un utilisateur dans une seule boucle et n'appelait `buffer.delete()` qu'après la boucle complète — un timeout LLM (`openai.APITimeoutError`, observé plusieurs fois en usage réel avec des instabilités réseau Azure) sur un seul message empêchait tous les autres messages du même batch d'être purgés, même ceux traités avec succès avant l'échec. Chaque message est désormais traité isolément (`try/except` par ligne, journalisé) : un échec laisse uniquement le message fautif en attente (retenté au tick suivant), les autres sont consolidés et purgés normalement. Vérifié en conditions réelles sur un batch de 36 messages pollués par des timeouts Azure intermittents : 27 traités avec succès en un seul tick, 9 en échec isolé (contre un blocage total des 36 auparavant). Tests : `tests/unit/test_processor.py::test_process_pending_isolates_failures_between_messages`.
- **Script de démo mémoire ne nettoyait pas Chroma** : `docs/script_presentation_demo_memoire.md` ne purgeait que Postgres (`DELETE FROM memory_episodes`...) — désormais insuffisant pour repartir sur une base propre puisque Chroma est réellement utilisé (cf. fix `@override` ci-dessus) : les anciens épisodes/faits restaient consultables via la recherche par similarité malgré un nettoyage SQL complet (observé en usage réel : réponse LLM injectant le contexte d'une session précédente pourtant purgée). Une commande de nettoyage des collections `velmo_episodes`/`velmo_memory` (pas `velmo_faq`) a été ajoutée à la Checklist pré-démo et au Nettoyage final.
